# Operations

## Processes

- `web`: logs to stdout (Next.js). Errors mapped to user-safe messages are logged with `[unexpected]`.
- `worker`: structured JSON logs (`level`, `time`, `worker`, `msg`, `jobId`, `type`, `attempt`, `error`, `ms`).

## Processing queue

`processing_jobs` is both the queue and the history users see.

```sql
-- Backlog and failures
select type, status, count(*) from processing_jobs group by 1, 2;
-- Stuck work (expired leases are reclaimed automatically)
select id, locked_by, locked_until, attempts from processing_jobs where status = 'running' and locked_until < now();
```

Failures retry with exponential backoff (30 s, 60 s, …) up to `max_attempts` (3). Permanent failures (content mismatch, unreadable media) don't retry. Authorized users can retry from the asset page, which re-queues the job.

## Uploads

Unfinished multipart uploads are aborted by the worker's sweep once `expires_at` passes (default 72 h), which also removes the never-completed version. Keep a bucket lifecycle rule as a backstop.

## Deletion and retention

Deleting folders, assets and projects is a **soft delete**. Bytes remain in storage and count toward the "In trash" figure on the Storage page. A retention purge job (hard-deleting objects and rows after a configurable period, per org setting) is scheduled for Phase 6. Until then, restoring is an administrator SQL operation (`update assets set deleted_at = null where …`).

## Backups and recovery

- **PostgreSQL**: enable point-in-time recovery on the managed service and test restores quarterly. The database holds all metadata, permissions and audit history.
- **Object storage**: originals are immutable once uploaded (new versions are new objects). Enable bucket versioning or cross-region replication according to your recovery objectives. Derived previews can be regenerated by re-running ingest.
- Consistency: after restoring the database to time T, objects uploaded after T are orphaned (not harmful). Objects deleted before T can only be recovered with bucket versioning.

## Monitoring checklist

- Queue depth and age of the oldest `queued` job
- Rate of `failed` jobs and of `auth.login_failed` audit events
- PostgreSQL connections (each process holds up to `DATABASE_POOL_MAX` app plus half that system connections)
- Storage growth (Storage page or `storage_locations`)
- Error tracking (Sentry/OpenTelemetry): the integration point is planned for Phase 6
